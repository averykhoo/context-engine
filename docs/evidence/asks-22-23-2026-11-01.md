## Fable opinion

# Fable opinion on ASK-22 and ASK-23 (2026-10-31; read: context.md, grep of REGISTER.md for INV-31)

## ASK-22: paste rules 1 and 2 into ~/.claude/CLAUDE.md, drop rule 3, then close CE-110.
- The global file is the only place every agent in every repo reads, and all three rules are genuinely
  absent from it (brief §2). The "Two shells" section is exactly their class: Windows/Git-Bash tool hazards,
  so this does not fight CE-40 ("machine facts stay") and adds nothing CE-40 would later have to move out.
- Rule 1 is a proven incident (AAR entry 13) and should keep the AAR's precise form, "never `bash <file>`
  a path held in a variable without checking its extension", not CE-110's blunter "never".
- Rule 2 is worth one line even at ~25% causal confidence: the cost is nil, the downside it guards against
  was a 104 GB, session-killing fork storm, and the substitute (`run_in_background` on one script) is
  already how this machine wants long jobs run. Label it "suspected cause, not proven" so nobody later
  cites it as settled; an honest rule beats a confident wrong one.
- Rule 3 is the part the brief and the rerank got wrong by carrying forward unexamined: `ulimit -u` in
  Git Bash (MSYS2) almost certainly does nothing. MSYS/Cygwin do not implement RLIMIT_NPROC; the builtin
  prints a fixed value and setting it is a no-op or an error. A rule that fails by passing is the house
  failure mode (global CLAUDE.md § Assurance traps), so do not paste it until it has been seen to work.
- Watch for: before pasting rule 3, sabotage it, e.g. `ulimit -u 200; for i in $(seq 300); do sleep 30 & done; jobs | wc -l`
  in Git Bash; if it reaches 300, the rule is dead and the real cap is the WSL/`.wslconfig` memory line or
  a process-count check in the script itself. Also, G-D1 caps apply only to repo CLAUDE.md, not the global
  file, so size is not a reason to refuse; keep it to three lines anyway.

## ASK-23: do not retire CE-145 yet; keep it at SOMEDAY until INV-31 carries the clause, then retire.
- My rerank line ("already tracked by INV-31") was wrong, and the verifier repeated it without checking:
  the register text names the @-import target, resume, /clear and the hook shell, and says nothing about
  compaction or the agent keeping its key (REGISTER.md::INV-31, grep 2026-10-31). Today CE-145 is the only
  board-visible tracker of that observation, and the owner asked for it by name five days ago (CE-79 log).
- The two trackers are not duplicates of the same wait: INV-31 waits on owner-run probes an agent cannot
  launch; CE-145 waits on a natural compaction in adhoc that an agent's own turn will witness. The second
  can be closed by an agent noticing; the first cannot.
- Folding is still the right end state, since a one-line observation target does not need a task, but the
  order matters: amend INV-31 first (register entries change only with code, so flag the exception in the
  commit), then retire CE-145 with `Closes:` pointing at the amendment. Retiring first loses the target.
- Watch for: the clause must say what counts as "seen" (first post-compaction turn runs with the old key,
  no second `session start` in the ledger) and name the evidence file to append to
  (docs/evidence/inv31-adhoc-probe-2026-10-23.md, compaction row). Without that, INV-31 becomes a line that
  prompts nobody, which is the exact loss the brief warns of. Keep the G-6 link in the amendment text.
