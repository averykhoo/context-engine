The agent's call on CE-141, made while building it in session 2026-10-30a. The brief asked for a table "generated with a guard that it is current", and DEC-81 said a generated status table "needs a generator and a guard". This call builds the generator and stores nothing, so there is nothing to keep current and no guard.

Options:
(a) A stored table, with a lint guard that it equals a regeneration. Rejected: the table depends on the board's states, so it goes red after every task close or new task until someone regenerates it.
(b) The same stored table, regenerated by task writes the way store._reindex regenerates the decision index. Rejected: store.derived() would make every commit that carries the table also carry the task-dir op lines of every other session (the commit.select rule from CE-125), which couples concurrent sessions.
(c) Record that the board plus the coverage map are enough. Rejected: the only map is frozen at 2026-10-12 and is stale (for example it gives G-T5 to CE-14, which is closed, while CE-34 is open), and a reader of the spec cannot combine the two by hand.
(d) Chosen: a read operation, `coverage` (CLI and MCP), that generates the table from what G-D12 already reads (the spec and the newest coverage map), plus the board and config.LINT_IDS. Nothing is stored, so it cannot go stale, and it needs no currency guard; that holds because the table is built at read time.

Known limits, as STATUS_RULES documents them: an open item that merely mentions a key makes that item "open work" (G-D12's limit too), and a DEFERRED or PROSE-ONLY row in the newest map outranks the board, so a component deferred and later built reads "deferred" until a new map is written.

Built in lane commit de47cc3, on main as 3ad5028. Cheap to undo: delete the one op (revert that commit). Revisit if readers need the status in a file (for example on GitHub); a CI job could then print it into an artifact instead of committing it.
